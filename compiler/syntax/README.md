# quince_syntax

The lexer, the parser and its CST now, and the formatter later. This file holds the contracts the spec leaves to the implementation: what a token is, which errors the lexer owns, the shape of the CST and where trivia sits in it, how the parser recovers from errors, and how the naming case is checked. The designs are in [`docs/design/m1-lexer.md`](../../docs/design/m1-lexer.md) and [`docs/design/m1-parser.md`](../../docs/design/m1-parser.md). The language rules are in the spec's [Lexical structure](../../spec/reference/lexical.md) chapter, and aren't restated here.

## Source text

- `decode_source(&[u8])` is the one place source bytes become text. Every caller that reads a file uses it before lexing.
- Each maximal run of invalid UTF-8 becomes one U+FFFD in `Decoded::text`, and `Decoded::replaced` records where. Each line that holds invalid bytes gets one E0014, at its first run.
- When `Decoded::is_lossy()` is true, the text isn't the file, so no tool may write it back. Every writer checks it: `fmt`, `fix` and the language server. For the same reason, `lex` gives no error in a lossy text a fix, and `parse` clears every fix in a lossy text, once, after all its stages, so the rule covers each of them.
- A file over 4 GiB, more than a `u32` offset can address, is an I/O error, not a diagnostic.

## Tokens

- `lex(&Decoded)` lexes decoded text into a `Lexed`, which holds its tokens and errors. `lex_str(&str)` lexes text that never came from bytes.
- A `Token` is a `SyntaxKind` and a byte length. A token starts where the one before it ends.
- Every byte belongs to exactly one token, so the token texts concatenate to the input. No token is empty.
- The lexer never fails and never stops early. An error produces a `SyntaxError` (byte offsets, a code, a message and fixes) and a token, and lexing goes on. `Lexed::diagnostics` turns the errors into `Diagnostic`s through a `LineIndex`.
- Trivia, which the parser skips:
  - `Whitespace`: a run of spaces and tabs.
  - `Comment`: `//` up to its line ending.
  - `BlockComment`: `/*` to the next `*/`, or to the end of the file when there is none.
  - `Bom`: a byte order mark at the very start.
  - `Error`: a run of characters that start no token, or one U+FFFD that decoding put in place of invalid bytes.
- `Newline` is one line ending: LF, CR LF, or a lone CR. A lone CR is an error, but it ends a line here as it does in `LineIndex`, so the parser's line ends agree with the line numbers in diagnostics. Each line ending is its own token.
- `DocComment` is `///` up to the line ending, but not `////`. Whether the parser treats it as trivia is the parser's call.
- An identifier is `Ident` whatever its case. Each keyword has its own kind (`FnKw`, `SelfTypeKw` for `Self`). Nothing else is special: `main`, `TaskScope` and the tag names are identifiers. `_` alone is `Underscore`.
- A number is an `Int` or a `Float`. A `.` is part of a float only with a digit after it, so `1..10` and `3.14.to_fixed(2)` lex as you'd expect. Right after a `.` token, with no trivia between, a number is a tuple position: a decimal integer with no point or exponent, so `pair.0.1` is `pair` `.` `0` `.` `1`. A minus sign is always its own token. Tokens don't hold values: `literal::int_value` and `literal::float_value` compute them from the text.
- A `"` string is `StringStart` (its `"`), then any number of `StringText` and interpolations, then `StringEnd` (its closing `"`). `StringText` is a run of text with its escapes, which `literal::string_value` decodes, and no escape spans two of them. An interpolation is `InterpStart` (`{`), its path as ordinary `Ident`, `SelfKw`, `Dot` and `Int` tokens, and `InterpEnd` (`}`), so names in strings are real tokens. A `}` alone is text. A test's name, the string after `test` and any spaces, doesn't interpolate (`r[test.name]`), so its `{` is text too, but its escapes are checked (`r[test.name-escapes]`). A string with no closing `"` on its line ends before its line ending, with no `StringEnd`, and the parser accepts it without one.
- A multi-line string, `"""` or `r"""`, has the same shape, and its `StringStart` and `StringEnd` are `"""`, or `r"""` for the raw form's start. Any other prefix before `"""` is an error (E0010, below), and its string is lexed as an `r"""` one, so its `StringStart` is that prefix and `"""`. Each line ending in it is a `StringNewline`. A `StringIndent` is spaces and tabs that aren't part of the value: those after the opening `"""`, the closing line's indentation at the start of each line and before the closing `"""`, and all of a line that holds only whitespace. A `"""` line takes a `"` string's escapes and interpolation, and a test's name doesn't interpolate in this form either. A raw line is one `StringText`. The value is the tokens between the string's first `StringNewline` and its last: each `StringText` decoded, unless the string is raw, each `StringNewline` between them a line feed, and each `StringIndent` nothing. The formatter re-indents a multi-line string by rewriting its `StringIndent`s, which leaves the value as it is.
- An identifier glued to a `"` is a literal's prefix, and the literal's `StringStart` holds both: `r"`, `b"`, or a tag such as `re"`. A keyword is never a prefix, so `test"adds"` is `test` and a string, and `_` isn't one either. A raw string or a tagged literal is `StringStart`, at most one `StringText` holding its raw body up to the next `"` on the line, and `StringEnd`. A bytes literal has the same shape, and its `StringText` holds its escapes, which `literal::bytes_value` decodes. None of them interpolate or span lines, and one with no closing `"` ends before its line ending, as a `"` string does. `literal::TAGS` lists the tags.
- A char literal is one `Char` token, quotes included, which `literal::char_value` decodes. Its body runs to the next `'` that an escape doesn't take, so `'\''` is one char, and one with no closing `'` on its line ends before its line ending.
- Punctuation is the longest match, except that `>` is always a token of its own. The parser forms `>>` and `>=` from a `>` and the token right after it, when no trivia sits between them.
- The lexer doesn't decide which line breaks end a statement. `SyntaxKind::continues_line()` is true for the kinds after which a line always continues: a comma, an opening bracket, `=`, a compound assignment, `=>`, `->`, and every binary operator but `>` and `*`. The parser decides `>`, `*` and the rest.

## Errors the lexer owns

The lexer reports each lexical problem once, and the parser must not report it again:
- An `Error` token is trivia. A fixture or a fix that adds a bad character puts it where trivia may go.
- A `;` is a `Semicolon` token, reported as E0002. The parser reads it as a line break that ends a statement, so `a; b` is two statements with only the E0002. It ends the statement outright: `a;` followed by a line that starts with `.` is two statements, not a method chain. Where a construct can't end, the E0002 is the only error: the parser reports nothing at a break that holds a `;`, so `fn f() ->; Int {}` is the E0002 alone. That includes the end of the file after a `;`, as in `fn f() ->;`.
- A `BlockComment`, reported as E0003, is a comment to the parser.
- A malformed number, reported as E0008, keeps its `Int` or `Float` kind, glued letters included (`1u8` is one `Int`), so the parser accepts it as a literal.
- An invalid escape, reported as E0006, stays part of its `StringText`, or its `Char`.
- A malformed char literal, reported as E0009, keeps its `Char` kind, so the parser accepts it as a literal.
- An interpolation that isn't a path, reported as E0007, is one `Error` token: up to and including the next `}`, or up to the next `"` or line ending, so the string goes on after it, and `"{"` still ends at its second `"`. Escapes don't count inside the braces. The lexer rejects a path that starts with `Self`, but it can't tell that a name such as `Config` is a type, so name resolution reports a path that starts with one.
- A string, raw string, bytes or tagged literal with no closing `"`, reported as E0004, has no `StringEnd`.
- An unknown tag, reported as E0010, is lexed as a tagged literal, with a raw body, and is that literal's one error: with no closing `"` it gets no E0004. So in `"say "hi" now"`, an unescaped quote, `hi" now"` is one literal with an unknown tag.
- `b"""` or a tag before `"""`, reported as E0010 at the prefix, is lexed as an `r"""` string, so its closing line closes it.
- A non-ASCII character in bytes, reported as E0011, stays part of its `StringText`.
- A control or bidirectional-format character in a literal or comment, reported as E0015, stays part of its token: a `StringText`, a `Char`, a comment, or the `Error` token of a broken interpolation.
- A multi-line string with no closing line, reported as E0005, runs to the end of the file with no `StringEnd`. Each line after the opening one is one `StringText`, with no escapes, interpolation or control characters checked, since it is more likely code than text.
- A string ends at its first `"""` that an escape doesn't take, as in `\"""` (escapes don't count in a raw string). When that `"""` follows text on a line, it is still the string's `StringEnd`, reported as E0012, so the rest of the file is lexed as code. The lines up to it are lexed as in a closed string, dropping the indentation they share.
- Text after an opening `"""`, reported as E0012 at the text without its trailing spaces, or at a second `"""` on that line when there is no text, as in `""""""`, is one `StringText`, with no escapes or control characters checked. A `"""` after it on that line is the string's `StringEnd`, so `"""text"""` can't swallow the file. A line that doesn't start with the closing line's indentation, also E0012, keeps the part of its indentation that matches as its `StringIndent`, and the rest is text.

| Code | Reported for | Fix |
| --- | --- | --- |
| E0001 | A run of characters that start no token, outside literals and comments | For a run of whitespace other than spaces and tabs, replace each with a space (`safe`) |
| E0002 | A `;` | At a line end, delete it: `safe`, or `needs-review` when the next line starts with `.`, which the deletion joins to the statement |
| E0003 | A block comment | When it covers whole lines, rewrite it as `//` lines (`safe`) |
| E0004 | A `"` string, raw string, bytes or tagged literal with no closing `"` on its line, at its `StringStart`. Not when a lone CR ends it, which only E0013 reports, or after an unknown tag | Insert `"` at the line end (`needs-review`), unless a `"` string or bytes literal ends with a `\`, which would escape it |
| E0005 | A multi-line string with no `"""` after its opening quotes, at those quotes | None |
| E0006 | An invalid escape in a `"` or `"""` string: unknown (`\q`), `\'`, `\}`, `\x`, a bad `\u{...}` or `\u` with no braces, or a `\` at a line end. In bytes: unknown, `\'`, `\{`, `\}`, `\x` without two hex digits, any `\u`, or a `\` at a line end. In a char literal: as in a string, but `\'` is valid | For `\'` and `\}`, and `\{` in bytes, delete the backslash (`safe`), unless the escape follows a `\u` with no closing `}`, which the deletion could join it to |
| E0007 | An interpolation that isn't a path: empty, spaces, any other body that isn't a path, or a `{` never closed | When the braces hold a path with spaces that each touch a brace or a `.`, delete them (`safe`) |
| E0008 | A malformed number: a misplaced underscore, an uppercase prefix or `E`, a prefix or exponent with no digits, a digit outside its base, a leading zero, or a suffix. Each problem is its own E0008, at most one of each kind per digit group | Lowercase a prefix or `E` (`safe`); remove a suffix (`needs-review`), unless a `.` and a digit follow it, as in `1x.5`, which would become a float |
| E0009 | A char literal that is empty or holds more than one Unicode scalar value, over the literal, or that has no closing `'` on its line, at its `'`. Not when a lone CR ends it, which only E0013 reports. An escape counts as one, valid or not | For more than one, make it a `"` string with the same value (`needs-review`), unless the body has an invalid escape or a control character, whose own fix comes first, or a name character or a `"` comes right before it, which the new `"` would join |
| E0010 | An identifier glued to a `"` that isn't `r`, `b` or a tag, at the identifier; or `b"""` or a tag before `"""`, at the prefix | None |
| E0011 | A run of non-ASCII characters in a bytes literal, other than replacements from decoding, which E0014 reports. A `\` before one is an E0006 instead | Replace it with the `\x` escapes of its UTF-8 bytes (`safe`) |
| E0012 | A multi-line string layout error: text after the opening `"""`, at the text, or at a second `"""` on that line when there is none; a line that doesn't start with the closing line's indentation, at its indentation, or at the line and its line ending when it has none; or, when no line starts with it, the closing line's indentation, reported once; or `"""` after text on a content line, at the quotes | For quotes after text, move them to a line of their own, indented as the lines share (`needs-review`, since they may have been meant as text). Otherwise none |
| E0013 | A CR not followed by LF, also inside a block comment or a multi-line string | Replace it with LF (`safe`), unless it ends an unclosed literal, or follows another CR, with which an LF would make one CR LF |
| E0014 | A line with invalid UTF-8, from `decode_source` | None |
| E0015 | A run of control characters other than tabs and line endings, or bidirectional-format characters (`r[lex.source.control]`), in a literal or comment. Not inside an invalid escape, which is an E0006, nor a bidirectional character in bytes, which is an E0011, nor in the unchecked text of a multi-line string | In a `"` or `"""` string, a test's name or a char, replace each with its `\u{...}` escape; in bytes, with its `\x` escape (`safe`). None in raw and tagged literals, comments, or an interpolation's braces |

Messages describe Quince, the same way for every input. An error says what Quince expects, such as the escapes a string takes or what a path is, and the lexer never looks for a construct from another language to call it out (decided by David, 2026-11-11). An E0006 in bytes gives the `\x` escapes for a `\u{...}` escape, and E0011 the `\x` escapes of the character, since both are Quince escapes. No message holds a control or bidirectional-format character: it names one by its code point, such as U+0007.

## The CST

The tree is a `rowan` tree, in the `cst` module. `parse(&Decoded)`, or `parse_str` for text that never came from bytes, gives a `Parse`: the root, a `File` node, and every error the lexer, the parser and the checks on its tree found, in source order. `Parse::diagnostics` turns them into `Diagnostic`s, as `Lexed::diagnostics` does.

- `SyntaxKind` holds the node kinds after the token kinds, and `QuinceLanguage` maps it to `rowan`. A node kind is named after the grammar production it holds, where there is one. `File` is the root, and `Skipped` holds the tokens the parser skipped while recovering from an error.
- The tree is lossless: its text is the input, and its tokens are the lexer's, in order, with their kinds. The exceptions are `GtGt` and `GtEq`, CST-only tokens that each hold a `>` and the token right after it, which the parser joins. No token is empty, and no node is, except the root of an empty file.
- The parser never builds the tree. It emits events: start a node, finish it, take the next significant token, join the next two, and report an error. The tree builder turns them and the lexer's tokens into the tree, and places every token the parser didn't read. Those are the trivia: the kinds for which `SyntaxKind::is_trivia()` is true, and doc comments that document nothing. `is_trivia()` covers the trivia under Tokens, plus `Newline` and `Semicolon`, which the parser reads only as the breaks between the tokens it sees.
- Where trivia goes:
  - Trivia before a node's first token goes outside the node, before it.
  - Trivia after a node's last token goes outside it too. So trivia between two tokens goes in the innermost node that holds both, unless the rule below takes it: a comment at the end of a block's last line goes in the block, before its `}`, and the blank lines between two declarations go in the node around both. Trivia before the first token and after the last goes in the root.
  - The exception: comment lines directly above a node whose kind `attaches_comments()` (a declaration, field, enum variant, member, or match or select arm) go inside the node, with their line endings and the indentation of the node's own line. A comment line starts a line, holds only comments and whitespace, and ends with a line ending. The run stops at a blank line, or at a line with anything else on it, such as code or a `;`. The indentation before the first comment stays outside.
  - For that rule, a comment is a `Comment`, a `BlockComment`, an `Error` token or a doc comment the parser left as trivia. So a comment at the end of a line of code never goes in the node below it. The byte order mark never goes inside a node: it belongs to the file.
  - Comments go in the outermost node that starts at the token below them, and only when that node's kind takes them. The builder writes them as soon as it opens that node, so a node opened inside it at the same token finds none left.

### Node shapes

A node holds its tokens and child nodes in source order. A part the code leaves out, or that an error stopped the parser before, is simply absent: there are no placeholder nodes. The kinds the parser builds so far:

| Kind | Holds |
| --- | --- |
| `File` | The declarations. |
| `FnDecl` | `DocComments` and `Attribute`s if present, as for every declaration of the file, then `pub` if present, `fn`, a `Name`, `Generics` if present, a `ParamList`, a `RetType` and `Effects` if present, a `Contract` per contract, and a `Block`. An interface's methods have no `Block`, an effect's operations neither contracts nor a `Block`, and a C function in a `foreign` block only its `RetType` after its `ParamList`. A `uses` after a bare function type in the `RetType` is the declaration's `Effects` (`r[effect.uses-return]`). |
| `ParamList` | `(`, `Param`s and their commas, and `)`. |
| `Param` | `var` if present, then `self`, or a `Name` or `_` followed by `:`, a type, and `=` and an expression for a default. A closure's is a `Name` or `_`, then `:` and a type if present. |
| `Contract` | `requires` and an expression, or `ensures`, then `(`, a `Name` and `)` if the return value is named, and an expression. |
| `RetType` | `->` and a type. |
| `TestDecl` | `test`, its name as a `Literal`, then `forall` and a `ParamList` if present, `Effects` if present, and a `Block`. |
| `ConstDecl` | `pub` if present, `const`, a `Name`, `:`, a type, `=` and an expression. |
| `ImplDecl` | `impl`, `Generics` if present, a `TypePath` and `for` if it implements an interface or an effect, a type, `{`, its members, and `}`. A member is a `FnDecl`, an `AssocType` or a `ConstDecl`, with its `DocComments` and `Attribute`s if present, as a declaration's are. |
| `InterfaceDecl` | Its declaration's start, as for `FnDecl`, then `interface`, a `Name`, `Generics` if present, `{`, its members, `AssocType`s and `FnDecl`s with no `Block`, and `}`. |
| `AssocType` | `DocComments` and `Attribute`s if present, `type` and a `Name`, then `=` and a type in an `impl`. |
| `EffectDecl` | Its declaration's start, as for `FnDecl`, then `effect`, a `Name`, and either `Effects` if present, `{`, a `FnDecl` per operation and `}`, or `=` and a `TypePath`. |
| `ForeignDecl` | Its declaration's start, as for `FnDecl`, then `foreign`, the library's name as a `Literal`, `Effects` if present, `{`, its `FnDecl`s and `ForeignType`s, and `}`. |
| `ForeignType` | `DocComments` and `Attribute`s if present, `type` and a `Name`. |
| `Import` | `import`, the package path's names and the `.` tokens between them, then `.` and `ImportNames`, or `as` and a `Name`, if present. |
| `ImportNames` | `{`, a `NameRef` per name and their commas, and `}`. |
| `StructDecl` | `DocComments` and `Attribute`s if present, `pub` if present, `struct`, a `Name`, `Generics`, then a `FieldList` and `requires` and an expression if present. |
| `FieldList` | `{`, `FieldDecl`s and their commas, and `}`. |
| `FieldDecl` | `DocComments` and `Attribute`s if present, `pub` if present, a `Name`, `:` and a type. |
| `NewtypeDecl` | Its declaration's start, as for `StructDecl`, then `(`, `pub` if present, a type, and `)`. |
| `EnumDecl` | Its declaration's start, as for `StructDecl`, with `enum`, then a `VariantList`. |
| `VariantList` | `{`, `Variant`s and their commas, and `}`. |
| `Variant` | `DocComments` and `Attribute`s if present, a `Name`, and `VariantFields` if present. |
| `VariantFields` | `(`, `FieldDecl`s and their commas, and `)`. |
| `AliasDecl` | Its declaration's start, as for `StructDecl`, with `type`, then `=` and a type. |
| `Attribute` | `@`, a `NameRef`, and an `ArgList` if present. |
| `DocComments` | The `DocComment` tokens before a declaration, a field, a variant or a member, and the trivia between them. |
| `TypePath` | Its names and the `.` tokens between them, whatever their case, then its `TypeArgs` if present. An effect in a `uses` list and a bound are `TypePath`s too. |
| `TypeArgs` | `<`, types and their commas, and `>`. The last item may be `Effects`, and in a bound an item may be a `NamedTypeArg`. |
| `NamedTypeArg` | A `NameRef`, `=` and a type: `Item = Int` in a bound. |
| `TupleType` | `(`, two or more types and their commas, and `)`. The unit type is the type path `Unit`. |
| `ParenType` | `(`, one type and `)`. The type is a `FnType` unless the node holds an error. `()`, an E0027, holds no type. |
| `FnType` | `fn`, `(`, the parameter types and their commas, `)`, then a `RetType` and `Effects` if present. |
| `Effects` | `uses`, then `*` or `TypePath`s and their commas. |
| `Generics` | `<`, `GenericParam`s and their commas, and `>`. |
| `GenericParam` | A `Name`, then `:` and bounds joined by `+` if present, or `uses` and a `Name`. |
| `Block` | `{`, its statements, and `}`. An expression statement is the expression's own node. |
| `LetStmt` | `let`, a pattern, `:` and a type if present, `=` and an expression. |
| `VarStmt` | `var`, a `Name`, `:` and a type if present, `=` and an expression. |
| `WhileStmt` | `while`, an expression, and a `Block`. |
| `ForStmt` | `for`, a pattern, `in`, an expression, and a `Block`. |
| `AssignStmt` | An expression, `=` or a compound assignment, and an expression. The left one is a place unless the statement has an E0026. |
| `IfExpr` | `if`, an expression and a `Block`, then `else` and an `IfExpr` or a `Block` if present. |
| `Name` | The `Ident` of a name being declared. |
| `NameRef` | The `Ident`, `self` or `Self` of a name being used, then, in an expression, the `TypeArgs` after an `Ident` when its `<` starts them. |
| `Literal` | One `Int`, `Float`, `Char`, `true` or `false`; a negative number, its `-` and its `Int` or `Float`, with any trivia between them; or a whole string: its `StringStart`, text, `Interp`s and `StringEnd`, which an unclosed string lacks. |
| `Interp` | An interpolation's `InterpStart`, the tokens of its path, and its `InterpEnd`. |
| `ListLit` | `[`, expressions and their commas, and `]`. |
| `Range` | An expression, `..` or `..=`, and an expression. |
| `Binary` | An expression, an operator other than a range's, and an expression. `>>` and `>=` are one token each. |
| `Prefix` | `-`, `!` or `~`, and an expression. |
| `Paren` | `(`, an expression, and `)`. |
| `Tuple` | `(`, two or more expressions and their commas, and `)`, or just `(` and `)` for the unit value. |
| `MapLit` | `{`, `MapEntry` nodes and their commas, and `}`, or `{`, `:` and `}` for the empty map. |
| `MapEntry` | An expression, `:` and an expression. |
| `Index` | An expression, `[`, an expression, and `]`. |
| `Try` | An expression and `?`. |
| `Call` | The callee, any expression, and an `ArgList`. A method call is a `Call` whose callee is a `Field`, and a struct literal or a variant is a `Call` too, since only name resolution can tell them apart. |
| `ArgList` | `(`, the arguments and their commas, and `)`. An argument is an expression or a `NamedArg`. The first may be an `UpdateArg`, and then each argument after it is a `NamedArg`, at least one. |
| `NamedArg` | A `NameRef`, `:`, and an expression if there is one. |
| `UpdateArg` | `..` and an expression: the base of a struct update. |
| `Field` | An expression, `.`, and a `NameRef` or a tuple position's `Int`. |
| `IsExpr` | An expression, `is` and a pattern. |
| `OrPat` | Two or more patterns and the `\|` tokens between them. None of them is an `OrPat`. |
| `WildcardPat` | `_`. |
| `LiteralPat` | A `Literal`. A negative number is one `Literal`, as in an expression. |
| `RangePat` | A `Literal`, `..` or `..=`, and a `Literal`. |
| `BindPat` | The `Name` of a binding: a name that stands alone and doesn't start with an uppercase letter. |
| `PathPat` | A `TypePath` with no type arguments: any other name, or a dotted path. Name resolution decides whether it is a constant or a variant. |
| `VariantPat` | A `TypePath`, `(`, then patterns, or `FieldPat`s and a `..` token, and their commas, and `)`. |
| `FieldPat` | A `NameRef`, `:`, and a pattern if there is one. |
| `TuplePat` | `(`, two or more patterns and their commas, and `)`, or just `(` and `)` for the unit value. |
| `MatchExpr` | `match`, an expression, and a `MatchArmList`. |
| `MatchArmList` | `{`, `MatchArm`s and their commas, and `}`. |
| `MatchArm` | A pattern, a `MatchGuard` if present, `=>`, and an expression or a `Block`. |
| `MatchGuard` | `if` and an expression. |
| `Closure` | `fn`, a `ParamList`, a `RetType` and `Effects` if present, and a `Block`. |
| `ReturnExpr` | `return`, and an expression if present. |
| `BreakExpr` | `break`. |
| `ContinueExpr` | `continue`. |
| `ConcurrentExpr` | `concurrent`, an `ArgList` if present, then a `SpawnList`, or a `ForStmt` for a fan-out. |
| `SpawnList` | `{`, `SpawnExpr`s and their commas, and `}`. |
| `SpawnExpr` | `spawn`, then `in` and the scope, an expression, if present, and an expression. |
| `BackgroundExpr` | `background`, `(`, a `Param` for the scope, `,` and an argument if present, `)`, and a `Block`. |
| `SelectExpr` | `select` and a `SelectArmList`. |
| `SelectArmList` | `{`, `SelectArm`s and their commas, and `}`. |
| `SelectArm` | A pattern, `=`, an expression, `=>`, and an expression or a `Block`. |
| `WithExpr` | `with`, `Handler`s and their commas, and a `Block`. |
| `Handler` | A `TypePath` with no type arguments, `=` and an expression. |
| `Skipped` | The tokens the parser skipped after an error, a bracket and what it holds included. |

Postfix forms nest to the left: `a.b(c)` is a `Call` of a `Field` of a `NameRef`. The parser opens such a node after its left side is parsed. The parser's own steps say which node a later one wraps, as rust-analyzer's `forward_parent` does, and one pass turns them into the builder's events, so the builder never sees a node opened out of order.

## Parsing

The parser reads the significant tokens: every token but the trivia and the doc comments. Each records the break before it: none, a line break, or a hard break, when a `;` comes between it and the token before. Nothing comes before the first token, so it has no break.

- **Doc comments** are taken by the declaration, field, variant or member whose first token they come before, into its `DocComments` node, and so become part of the tree's significant tokens. Any other doc comment stays trivia and is an E0023: one in a block, after an attribute, before an `import` or a closing bracket, at the end of the file, and one after code on its line, even when a declaration follows. The doc comments before one token that document nothing are one E0023, whose fix makes each an ordinary comment. Doc comments in tokens skipped after an error are part of that slip, so they get none.
- **Attributes** come after the doc comments and before `pub`. Each goes on a line of its own, and the next line that isn't blank continues what they apply to. Something after an attribute on its line is an E0016. When it can start what the attribute applies to, the fix moves it to the next line. A keyword after `@` is an E0016 at the keyword, and the declaration after it is still parsed.

- **Where a break ends a construct.** In a line context (the file, a block, or the body of an `impl`, `interface`, `effect` or `foreign` block), a break ends the statement or declaration unless the token before it continues the line (`SyntaxKind::continues_line()`), the next token is `.`, or the parser is in a `fn` header, a declaration's, a closure's or a function type's, and the next token is `->`, `uses`, `requires`, `ensures` or `{`. A block is a line context of its own, so a header around it, as around a block in a contract, doesn't reach its lines. A hard break always ends it. In a list (parentheses, square brackets, angle brackets, and braces of fields, variants or map entries) a break before a `,` or the closing bracket is spacing, since the list reads them by kind. Elsewhere in a list the same rules apply, so a line that starts with `-` or `(` is a new item, and a missing `,` before it is an E0016 with its fix. A block inside a list is a line context again.
- **A line break too early.** When a line break ends a construct and the next line starts with a token that can't start a statement but continues the construct, the parser reports an E0018 at the break and parses on as though the lines were joined, so the tree is the joined one. Those tokens are `=` and the compound assignments, every binary operator but `-`, `?`, `:` after the name in `let`, `var` or `const`, `uses` after an `effect` or `foreign` header, `for` after an `impl`'s interface or effect, and a `{` where the construct needs its body next: after an `if` or `while` condition, a `match` subject or a `for` iterable, after `else`, after a `struct`, `impl`, `interface`, `effect`, `foreign`, `enum` or `test` header, and after `concurrent`, `select`, a `with`'s handlers and a `background`'s parentheses. At the top of a file a `{` can only be a struct's fields, so a struct's joins although a struct with no fields has no braces. `else` on the line after an `if`'s `}` is an E0018 in a list too. A hard break never joins.
- **Errors.** Every syntax error is reported once, and then the parser skips to a sync point, reporting nothing more until it next takes a token as part of a construct. The skipped tokens go in a `Skipped` node, and a bracket the skip meets is skipped up to its closing bracket. In a list, a `<` counts as a bracket, closed by `>`, so a skip there stays out of type arguments.
  - A list syncs at its next `,` and at its closing bracket. Type arguments and generics are lists closed by `>`, so their errors stay inside them, and a closing bracket further out closes them with an E0017 at the `<`. So does a `{`, since no type holds braces, so a header whose generics or type arguments go wrong still finds its body. A line context syncs at its next break, which ends the member that went wrong. An `impl`, `interface`, `effect` or `foreign` header syncs at the `{` on its line, so its body is still parsed as its body.
  - An `impl`, `interface`, `effect` or `foreign` header that parsed, its generics or type arguments closed at the break with an E0017 included, and ends its line where its `{` belongs is one E0016 at the line break. The parser goes on as though the `{` were there: the lines after it are the body's members, up to its `}`, and the first member reports its own slips, as after a real `{`. That `}`, with no slip in the body, gives the E0016 a fix that inserts ` {` after the header (`safe`): the fix says the `{` is all that's missing. With no `}`, the body closes where a body would at its missing `}`, at a line that only the file holds or at the end of the file, with no E0017 and no fix, since the `{` alone would leave the body unclosed. After a slip on the header's line no body is assumed, since the header may not take one, as an `effect` that names another doesn't.
  - A line in the file or a body that starts no declaration or member is one E0016, and a `{` on it opens a block that is skipped to its `}`, the lines in it included, with nothing more reported. In the file the block is skipped as a body, which a line that starts a body's member doesn't close, so a misspelled `interface` loses its methods with it. In a body it is skipped as a block, which a member start closes.
  - A token at the start of a line that can only start a member of some open container closes every construct inside the innermost such container, with an E0017 at each opening bracket it closes. For the file those tokens are `fn` and a name, `struct`, `enum`, `type`, `interface`, `impl`, `effect`, `foreign`, `import`, `const` and `test`, each also after `pub`. For the body of an `impl`, `interface`, `effect` or `foreign` block they are `fn` and a name, `type` and `const`. For struct braces, enum braces and a variant's fields they are `pub` and a name. For a block they are `let`, `var` and `while`. The check looks past attributes to the token after them, so a member start after an attribute line closes what it closes, with no error at the `@`.
  - The condition of an `if` or a `while`, the subject of a `match` and the iterable of a `for` sync at the `{` on their line, and the braces are still parsed as the block or the arms. One missing from its line is taken from the next line, and braces missing after it are part of that slip. So is the pattern after `let` or `for`, and what is missing after it. A slip in a `for` before its `in` is skipped up to the `{` on its line too.
  - A closing bracket that matches a bracket further out closes everything inside it, with an E0017 at each opener. One that matches nothing open closes the innermost list in its place, with one E0016 that names the bracket expected, and in a line context it is skipped as an E0016. The end of the file closes everything still open, with an E0017 at each opener.
  - An arm's `=>` closes the brackets opened in the arm, with an E0017 at each opener, so the arms after it still parse. A block in the arm stops this: its lines are a line context again, so a `=>` in them is an ordinary E0016.
  - A bracket closed while the parser is skipping after an error gets no E0017, since that error covers the slip.
  - After a bracket closes without its closing bracket, what the constructs around it lack is part of that slip, until the parser next takes a token. A line break there ends them, whatever token comes before it.
  - An E0016 after a list item, at an item that starts the next line, has a fix that inserts the `,` (`needs-review`).
  - Braces where an expression goes that hold no entry's `:` before their `}` hold statements, when an item lacks its `:` and the braces end or a line starts after it: one E0016 at the `{`, "found a block". Braces with an entry's `:` are a map, and the item gets "expected `:`".
  - A map literal's list that a block's member start (`let`, `var` or `while` at the start of a line) closes before any entry's `:` was a block, which can't go where an expression goes. That is one E0016 at the `{`, not an E0017, and the parser skips the rest of the block up to its `}`. A map with an entry before that line is a map missing its `}`, an E0017.
- **Operators.** The parser accepts any mix of binary operators and builds the tree of the usual reading, then reports what the spec forbids. The usual reading puts the operators with no level where the spec's examples do, so the order, tightest first, is postfix, prefix, `*` `/` `%`, `+` `-`, `<<` `>>`, `&`, `^`, `|`, `..` `..=`, comparisons, `&&`, `||`. Every level groups to the left, comparisons and ranges included, and their chains are E0020s.
  - A `>` and a `>` or `=` right after it, with no trivia between, are one operator, `>>` or `>=`, which the tree holds as one `GtGt` or `GtEq` token. A closing `>` of type arguments is never joined.
  - After a binary operator a line break is spacing, `*` and `>` included, which `continues_line()` leaves to the parser. After `-` it is spacing too, since `-` can be binary, but after `!` or `~` it ends the line.
  - A `<` after a name in an expression is examined by parsing ahead: the parser parses type arguments, and keeps them when they parse with no slip and the token after their `>` is one that may follow them. Otherwise it goes back to the `<`, dropping what it parsed and any error, and the `<` is less-than. While parsing ahead, the first slip makes the parser see the end of the file, so what it has open closes at once. It records the answer for every `<` it parses type arguments from, nested ones included, so no `<` is parsed ahead from twice and a file is parsed in linear time.
  - A `-` in prefix position, directly followed by an `Int` or `Float` that no postfix operator follows, is part of a `Literal` with it.
  - E0019 is reported at each operand that needs parentheses, and E0020 at the second operator of a chain, once per chain. Neither is reported for an operator any of whose operands holds a syntax error, a missing operand included, since that error is the slip.
- **Assignment.** A statement that starts with an expression becomes an assignment when `=` or a compound assignment follows it on its line. The left side is parsed as an expression and then checked against `grammar.place`: a name or `self`, then `.` and a name or a tuple position, or an index, any number of times. Assignment is a statement, so a second `=` is an E0016 where the statement should end, and `=` in a condition or a list is an E0016 there.
- **Patterns.** A pattern is parsed after `let`, `for` and `is`, and at the start of a match arm. `|` in it is always alternation, and a line that starts with `|` continues the pattern, an E0018, as a line that starts with a binary operator does. Case decides one thing: a name that stands alone, with no `.` or `(` after it on its line, is a `BindPat` unless it starts with an uppercase letter. Any other name or path is a `PathPat`, or a `VariantPat` when `(` follows it on its line, so `point(x)` is a variant too. A `.` on the next line continues the path. The first item in a variant's parentheses decides how its fields go: `name:` or `..` starts fields by name, and anything else fields by position. A field by position after one by name, and the reverse, is an E0016, and so is an item after `..`. A pattern has no prefix minus, so a `-` and the number after it are one `Literal`, whatever lies between them: `- 5` is `-5`. A `-` before anything else is an E0016. A range's bounds are literals, both of them. `()` is the unit value, and one pattern in parentheses is an E0016. A string pattern with an interpolation is an E0016 over its first one: the string is whole, so the pattern goes on and no recovery starts. It counts as a slip for the operator checks around the pattern, so `x == y is "{z}"` is the E0016 alone.
- **`is`** binds as a comparison does, and its right side is a pattern. It doesn't chain, so `a is A == b` and `a == b is C` are E0020s, with no fix, since `is` points no way (`r[expr.op.compare.split]`). A pattern is no operand, so an operator that binds tighter than a comparison after it, as in `x is A + 1`, is an E0016 at the operator, which stops the operators around it.
- **`match`.** Its arms are a comma-separated list, so a line break before a `,` or the `}` is spacing, and a block in an arm is a line context again. Every arm ends with a `,`: a `}` right after an arm is an E0016 whose fix inserts the `,` (`safe`), unless an unclosed string or char ends the arm's line, whose slip it is. A missing `,` between arms on separate lines is the list's E0016, whose fix is `needs-review`, unless such a literal ends the first arm's line: then it is that slip too, and the next arm is parsed. In an arm `{` after `=>` starts a block. Comment lines directly above an arm go inside it.
- **`for`** is a statement, as `while` is, and isn't one of a block's member starts, since a `concurrent` loop can sit in a list.
- **Members.** An `impl` holds methods, associated types (`type`, a name, `=` and a type) and constants. An `interface` holds associated types with no `=`, and method signatures with their contracts and no body. An `effect` holds operations, signatures with no contracts, or names another effect after `=`. A `foreign` block holds C types (`type` and a name) and C functions, which take named parameters and a return type and nothing else. A keyword can't be a C name. A signature ends its line, so a body after it is an E0016, and the skip takes the body whole. Only an `impl`'s methods and constants take `pub`. One anywhere else in a body is an E0016, and the member is parsed on. Taking the `pub` ends the recovery from a slip on the line before, as a member start does, unless the rest of the line is no member. A `const` in an interface is an E0016 (`r[item.const.assoc.no-interface]`).
- **Closures.** `fn` and `(` starts a closure, and `fn` and a name a declaration, so only the second is a member start, in the member-start check and in the scans that stop at one (the attribute look-past, and the scans for a map's `:`). A closure on a line of its own closes nothing.
- **`return`, `break`, `continue` and `spawn`** are parsed only where an expression goes, never as an operand, so `1 + return 2` is an E0016 at `return`. `return` takes an expression that starts on its line, all of it, and `return` on a line of its own is bare, as is `return` before the block's `{` at the top of a condition. `break` and `continue` take nothing, so a value after them is an E0016 where the statement or list item should end.
- **`spawn`** takes an expression that starts on its line. `spawn in` takes the scope first, a postfix expression, so a `(` after the scope's name calls it. In a `concurrent`'s braces each item is `spawn` and an expression, with no `in`.
- **`concurrent`, `background`, `select` and `with`.** The spawns in a `concurrent`'s braces are a list. A fan-out's `for` is parsed as a `for` loop, so its iterable is a condition's (`r[expr.block.cond-brace]`). A `background`'s parentheses hold the scope, whose type must be the name `TaskScope`, at most one argument, and a trailing `,` if present. As in a list, a `,` after a slip in the scope goes on to the argument, and after a slip in the argument the rest skips to the `)`. A `select`'s arms are a `match`'s list: an arm's `=>` closes only the brackets opened in its own arm, in a `select` inside a `match` arm too. A `with`'s handlers aren't in brackets, so a trailing `,` is an E0016. A handler's value is a condition in the sense of `r[expr.block.cond-brace]`, so `{` where it starts is the block. Handlers missing from the line of `with` are taken from the next line, as a missing condition is, when it starts with an effect's path and `=`. A next line that starts with `{` is the block, and any other line is a statement of its own. After a slip in a handler the rest of its line is skipped up to the `{`, and a `,` right after the slip goes on to the next handler. The braces of each of these go on the line of what comes before them, as a body's do, so on the next line they are an E0018.
- **Contracts** come after the signature's `uses`. The expression starts on its contract's line: a line that starts with `{` or another contract continues the header, so it is the expression missing, an E0016 at the line break. `ensures` and a name alone in parentheses always names the return value, and the condition follows. The condition is a condition in the sense of `r[expr.block.cond-brace]`, as an `if`'s is, so `{` where an expression starts is the body. Something after a whole condition on its line is an E0016 that expects `requires`, `ensures` or `{`, and the rest of the declaration is skipped, as after a return type, since the first `{` after it may not be the body's. After a slip in a contract, the parser skips to the next contract or the body's `{`, never to a `{` inside a later contract, so the next contract and the body are still parsed, and a body missing after the slip is part of it.
- **`if` and `else`.** `if` is an expression. At the top of an `if` or `while` condition, a `match` subject, a `for` iterable, a contract's condition or a `with` handler's value, `{` is the block, the arms or the body, never a map (`r[expr.block.cond-brace]`): a `{` where an expression goes there is an E0016. A closure, `concurrent`, `select`, `with` or `background` takes its own braces anywhere. Braces that hold an entry's `:` at their top, `{:}` among them, were meant as a map, the same test a map's own entries use: the fix puts them in parentheses (`needs-review`), and the parser parses the map, so the rest of the condition and the block parse as written. Other braces are the block, and the condition's expression is missing. Braces that hold a comment get no fix. A slip in a condition is skipped up to the `{` on its line, and a condition missing from its line is taken from the next line. `else` goes on the line of the `}` before it, and on the next line it is an E0018 (above).
- **Errors the parser leaves to the lexer.** Beyond the lexer's own list (above):
  - The parser drops an error it would report right after an `Error` token, with only trivia between, so `let x = $` is the E0001 alone.
  - An unclosed one-line string or char closes, at its line's end, the parentheses and square brackets opened on that line, with no E0017, and the parser reports nothing on that line. A block's `{` stays open. A list item that starts the next line needs no `,` before it, since the missing one may be inside the literal: the parser parses it as the next item and reports nothing. An item that can't start after the line break, such as a parameter, is skipped up to the list's next sync point instead.
  - When a multi-line string or a block comment runs unclosed to the end of the file, the parser reports nothing at the end of the file and gives no E0017 for what the end closes.
- **Loop safety.** Every parser loop takes a token, closes a construct or exits. Debug and fuzz builds panic when the parser looks at the tokens 256 times without taking one, closing a construct or completing a node.
- **The nesting limit.** A deep enough input would overflow the stack, which aborts the process rather than panicking. The parser recurses, and so do the tree's consumers and dropping the tree. So the parser bounds the tree's depth, `NESTING_LIMIT`, 256 levels with the file at level 1, and consumers may recurse over a tree.
  - The parser checks the depth where it recurses: before an expression, a prefix operator's operand, a block, a type and a pattern. An `else if` recurses through its condition's expression. A left-associative chain, such as `a + b + c` or `x.a().b()`, loops in the parser but nests in the tree, so each step checks the depth of the node it wraps too: each completed node records its height. A method call is two steps, its field and its call, so about 128 chained calls reach the limit. The few nodes a construct opens before its next check, such as a match arm around its body, can go a little deeper, at most 4 levels in `tests::nesting`.
  - Past the limit it reports E0022 at the token that goes past it and skips to the end of the innermost construct: its closing bracket in a list, or its line's end, the current token at least, so a loop over a block's lines always moves on. The skip goes past a nested arm's `=>`. Each completed node also records whether it holds an E0022, so a chain step around it past the limit, as in `((x).a).a`, is part of that slip, and the levels past the limit are one error. Two parts that each go past it on their own, such as a parameter's type and the return type, are two.
  - While parsing ahead from a `<` the E0022 is a slip like any other, so `g(a < b, a < b, ...)` is comparisons with no error. Whether type arguments parse past the limit depends on how deep the parser was, so none around the slip is recorded, and the parser parses ahead again from each `<` it meets later: at most a limit's levels each, so still in linear time.
  - Measured in a debug build on a 2 MiB thread, the stack of a Rust test thread, before the limit: nested list literals took the most stack, about 3.2 KB a level, and overflowed past 644 levels. Parentheses took 2.4 KB, blocks and maps 2.1 KB, and the rest less. Building, walking and dropping the tree overflowed past about 4,400 levels. So 256 levels use at most about 830 KB, with room to spare. `tests::nesting` nests each construct 10,000 deep on such a thread.
- **The fuzz check.** `fuzz::check_parse` decodes and parses any bytes and panics unless the invariants hold: no loop, a lossless tree whose tokens are the lexer's, error ranges and fix edits inside the text on character boundaries, and a tree within the nesting limit. It is compiled for tests and under the `fuzz` feature only. A unit test runs it on every fixture and every seed in `fuzz/testdata/`, a `testdata` folder so nothing compiles them, and the `cargo-fuzz` target in `fuzz/` on what the fuzzer makes (`AGENTS.md` has the command). The seeds nest near the nesting limit, since mutating small fixtures rarely builds a hundred balanced levels. A crash's input becomes a seed and a regression test.

## Naming case

`parse` runs the `validate` module over the finished tree, whatever errors it holds, and adds its errors to the parser's. It checks the naming case of the names declared in source (the spec's Naming section) and nothing else so far. The case of file names and of the manifest's package name is checked by the stage that reads them (M2).

- **Where.** Only a `Name`, a name being declared, is checked. A `NameRef` is a use, and a use is wrong only when its declaration is, which gets the error. So `width:` alone in a variant pattern, which binds `width`, isn't checked: it names a field, a `NameRef`. A name the parser skipped while recovering is in no `Name`, so it isn't checked either. Nor is a name glued to one of the lexer's `Error` tokens, as `bauche` is in `Ébauche`: the lexer split one identifier, and its E0001 covers that slip, as the parser drops an error right after an `Error` token.
- **Which class.** The node around the `Name` decides:
  - `snake_case`: a function, including an interface's method and an effect's operation; a parameter, including a closure's and a `background` scope's; a `let` or pattern binding (`BindPat`); a `var`; an `ensures` binder; a field, of a struct or a variant; a package's name after `as` in an import.
  - `PascalCase`: a struct, newtype, enum, alias, interface, effect, associated type, variant, type parameter and effect variable (`uses E` in generics).
  - `SCREAMING_SNAKE_CASE`: a constant, in the file or an `impl`.
  - None: any `Name` inside a `foreign` block, which keeps its C spelling.
- **E0021.** A name not of its class, including one that fits no class, is one E0021 over the name. The message names the class and what the name declares, then gives the name written in that class: its words, split at underscores, where a lowercase letter or a digit meets a capital, and before the last capital of a run that a lowercase letter follows (`HTTPServer` is `http` and `server`), joined in the class's case. When that gives no name of the class, or gives a keyword, the message gives none: `const N` is `N` in `SCREAMING_SNAKE_CASE`, which takes two letters, so only the author can choose a new name. E0021 has no fix in M1, since renaming a declaration needs its uses, which name resolution finds.
- **Patterns.** Case decides whether a name in a pattern binds (see Parsing), so `Second` in `let (first, Second) = p` is a path, which name resolution checks, and `_rest` is a binding, with an E0021 that suggests `rest`.
